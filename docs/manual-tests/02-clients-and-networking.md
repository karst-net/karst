# Manual tests: clients and networking

Run the common client rows on each supported beta platform: Linux x86-64 and
arm64, macOS Apple Silicon and Intel, and Windows x64. macOS uses
`Karst.app` and its `KarstPacketTunnel` Network Extension; it no longer ships
the `karstd` LaunchDaemon/TUN backend. Mark a platform row `Not applicable`
only where the product explicitly says the capability is not available (for
example host DNS in userspace mode, or DNS integration in the current macOS
Network Extension build).

| ID | Exercise | Steps | Expected result |
| --- | --- | --- | --- |
| CLI-01 | Install and boot client | Install the platform package/installer as a local administrator; reboot; uninstall afterwards in a disposable VM. On macOS, launch `Karst.app` from `/Applications`, approve the one-time System Extension prompt if shown, and verify its menu-bar item returns after login. | The client starts at the documented scope without exposing an enrollment secret. On macOS the signed package installs `Karst.app`, its per-user LaunchAgent, and the Packet Tunnel System Extension—not a LaunchDaemon. The macOS uninstaller leaves extension state and may require manual removal of the Network Extension; record that cleanup before judging the host restored. |
| CLI-02 | Platform integration | Enroll once using the normal platform path. Verify interface/address, routes, protected identity storage, and peer connectivity. On macOS, use `Karst.app` → **Enroll…**, then inspect its menu for interface/MTU, peer state and transport and inspect System Settings for the Karst VPN/Network Extension. | The correct platform mechanism is used: Linux service/TUN, macOS `KarstPacketTunnel` `NEPacketTunnelProvider`, Windows service/TUN or documented userspace path. macOS identity/configuration is under `/Library/Application Support/dev.karst.packettunnel`; never record its contents. |
| CLI-03 | Userspace mode | On platforms that offer it, enroll/select userspace mode and send allowed traffic. Inspect DNS status. Mark macOS `Not applicable`: the shipped Network Extension client has no selectable userspace mode. | Connectivity works without elevated TUN privileges where userspace mode exists; the client explicitly reports any host-DNS limitation rather than claiming integration. |
| CLI-04 | Setup recovery | Interrupt guided setup after identity creation, then resume it. On macOS, reopen `Karst.app` and use **Re-enroll…** with a fresh invitation (rather than `karst setup --resume`). Also try malformed invitation input. | Recovery uses the saved identity safely; malformed input fails clearly without replacing identity or enrolling a node. On macOS, a successful recovery changes the menu from **Enroll…** to **Enrolled as …** and **Re-enroll…**. |
| CLI-05 | Status and shutdown | On Linux/Windows, run `karst status`, `version`, `metrics`, `down`, and status again. On macOS, inspect `Karst.app`'s textual menu state (interface/MTU, peers, session transport and throughput), quit the app, then reopen it and confirm the System Extension/tunnel is independent of the menu-bar process. | CLI output identifies peer/session/MTU and version; metrics are Prometheus text; CLI shutdown is clean and reports an unavailable daemon afterwards. On macOS, **Quit** exits only `Karst.app`; it must not be represented as disconnecting or removing the Packet Tunnel. |
| NET-01 | Mesh DNS | Configure a mesh zone and resolve an enrolled peer, an unknown mesh name, and a public name. Mark the current macOS Network Extension build `Not applicable`: it deliberately does not configure DNS settings. | On supported DNS-integrating clients, peer resolves from the netmap; unknown mesh name is authoritative NXDOMAIN and is not leaked upstream; public name follows normal resolver policy. |
| NET-02 | Split DNS | Add an authorized split domain and upstream. Query matching and nonmatching names; make the split upstream unavailable. Mark the current macOS Network Extension build `Not applicable`. | On supported DNS-integrating clients, matching queries go only to the split upstream; nonmatching names do not; split failure is SERVFAIL, never global fallback. |
| NET-03 | DNS lifecycle | Start the client, compare host resolver state with its backup, stop/crash it, run `karst dns revert`, and restart. Mark the current macOS Network Extension build `Not applicable`. | On supported DNS-integrating clients, DNS changes are transactional and original resolver state is restored in every stop/failure path. |
| NET-04 | DNS diagnostics | Run `karst dns status` and `karst dns query` for mesh, split, and public names. Mark the current macOS Network Extension build `Not applicable`. | On supported DNS-integrating clients, the displayed listener, host integration, routes and explanation agree with observed resolution. |
| NET-05 | Subnet router | Enable forwarding on the gateway, create a restricted CIDR route, authorize one recipient group, and test both an authorized and unauthorized client. | Only recipients receive/use the route; authorized traffic reaches the LAN with a return path; ACL still limits destination access. |
| NET-06 | Exit-node consent | Publish default-route prefixes, confirm they are not auto-applied, use `karst exit-node use ROUTE_ID`, test public egress, then disable it. On macOS, arrange the active recipient exit route through the control-plane test setup instead: `Karst.app` has no local exit-selection UI. | Selection is explicit and persistent on clients that expose selection. macOS installs only an already-active recipient exit route; traffic uses it only while active, and removal restores ordinary routes. |
| NET-07 | Route resilience | Disable/delete the gateway route during use and restore it. On macOS, observe the route change after the Packet Tunnel's health poll rather than a CLI map update. | The client removes or marks the route unavailable without retaining a black-hole default route; restoration is reflected on the next map update (within a few macOS polling intervals). |
| NET-08 | macOS managed-device detection | On a macOS test device, first confirm ordinary self-service enrollment via `Karst.app` and ordinary VPN disconnect/removal through System Settings. Then install the sample profile (`sudo profiles install -type configuration -path dev.karst.packettunnel.example.mobileconfig`) on a separate device and reopen `Karst.app`'s menu. | Personal-mode device: no regression, Enroll/Re-enroll work as before and the user retains the normal System Settings controls. Profile-installed device: menu shows "VPN configuration managed by your organization"; System Settings shows the profile's removal control greyed out or password-gated. |
| NET-09 | macOS kill switch | With the managed profile active and the tunnel connected, force the engine to fail mid-session (kill the extension process or corrupt its `config.toml`/socket state), then attempt to reach the open internet from another app. | After the fault has settled, no traffic escapes the tunnel while the engine is down. Record the macOS version and real-hardware model: this test validates the still platform-dependent `IncludeAllNetworks` behavior for this provider; it is not a claim of an absolute client-side kill switch. |
| NET-10 | macOS reconnect and route-churn reassert | Toggle Wi-Fi off/on (or sleep/wake) while connected; separately, toggle an exit route active/inactive from another enrolled peer mid-session. | The tunnel automatically re-establishes via the on-demand rule; the exit-route change is reflected within a few polling intervals (about 2–10 seconds), without a full tunnel restart. |

Platform-specific evidence: package/installer version, service or Network Extension state, interface/route view, secure-store confirmation without secret values, and before/after DNS state where DNS integration is supported. For macOS, also retain the System Settings Network Extension view and the menu's textual state; do not retain invitations, identity keys, or `config.toml`.

# `UDP_GRO`, implemented for real (issue #120), 2026-09-12

Phase B of issue #120, following the io_uring spike
(`docs/measurements/io-uring-spike-2026-09-12.md`), which found `UDP_GRO`
correctly implemented was the actual win, not io_uring. This is the shipped
implementation: `karst-transport/src/sys.rs`'s `recv_batch` now requests and
parses the `UDP_GRO` cmsg and splits a coalesced read itself, and
`UdpTransport::bind`/`bind_reuseport` enable the sockopt best-effort.

`UDP_GRO` was attempted once before and reverted: enabling the sockopt alone
passed every loopback unit test and then took two real hosts to 100% packet
loss, because the receiver never read the cmsg saying a buffer held several
coalesced datagrams (see the postmortem `sys.rs` carries next to its GRO
code). Two questions therefore had to be answered with real evidence before
calling this done, not just one:

1. Is it faster? — already measured in the spike doc.
2. **Is it correct** against a real coalesced kernel read, not just a
   synthetic one? — this is what the previous attempt got wrong, and what
   this measurement is for.

## Method

`bins/karstd/examples/gro_verify.rs` (throwaway, deleted after this run —
its result lives here instead). Real two-host run, `turing`↔`lovelace`, same
3 Gbps bond as every other measurement in this series
(`10.10.10.1`↔`10.10.10.2`), 15 s, `BATCH`-sized `send_batch` calls.

Unlike a throughput benchmark, this checks **content**: every datagram
carries an 8-byte little-endian sequence number followed by a fill pattern
deterministic in that number. The receiver calls the real, production
`UdpTransport::recv_batch` — not a reimplementation — and for every
`Received` entry recomputes the expected fill from the sequence number it
decodes, comparing it against what actually arrived at that entry's own
`slot`/`offset`. A mismatch is **corruption**; a missing sequence number is
ordinary UDP loss, and the two are counted separately, because a metric
that conflated them is exactly the kind of number that would have hidden the
original bug.

It also detects real coalescing directly rather than inferring it from CPU
usage: within one `recv_batch` call, each of the `BATCH` physical `recvmmsg`
slots is used at most once, so two `Received` entries sharing a `slot` in the
same call can only mean `UDP_GRO` actually coalesced that physical read.

## Result

| Metric | Value |
|---|---:|
| Sent | 1,335,840 |
| Received | 1,243,061 |
| Max sequence number seen | 1,243,090 |
| Loss | 30 datagrams (0.002%) — ordinary UDP loss under load |
| **Corruption** | **0** |
| Truncated/malformed reads | 0 |
| **Entries from a coalesced slot** | **995,228 (80% of received)** |

**Zero corruption across 1.24 million real datagrams, 995,228 of which came
from a real, kernel-coalesced `UDP_GRO` read** — not a synthetic or
loopback-only test. This is the direct evidence the previous attempt did not
have: real coalescing at scale, with byte-exact splitting on every one of it.
Combined with the spike's throughput/CPU numbers (32% less receive-side CPU
for comparable throughput vs. plain `recvmmsg`), both halves of "faster and
correct" are now measured, not assumed.

## What this does and does not close out

This directly answers issue #120's acceptance criteria: `io_uring` was
benchmarked against the existing batched I/O and did not justify a fast path
(see the spike doc); `UDP_GRO` did, was implemented with a supported
fallback (best-effort `setsockopt`, silent no-op on kernels/environments
that lack it — see `sys::enable_gro`'s doc comment), and has regression
coverage: direct unit tests for the splitting logic
(`crates/karst-transport/src/sys.rs`'s `gro_tests`), integration tests
proving ordinary traffic is unaffected (`crates/karst-transport/tests/batched.rs`),
and this real two-host run proving coalesced traffic is handled correctly.

Not covered here: a long-duration soak with GRO enabled (the existing
12-hour soak in this directory predates this change). Worth doing before
leaning on this in a stability claim the way the soak backs the Phase 2 exit
criterion, but the correctness question this measurement exists to answer —
does the split logic hold up against real coalescing — has a clear answer
now, at real scale, not just a plausible one.

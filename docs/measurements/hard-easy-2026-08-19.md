# Hard/easy NAT traversal — does the birthday technique actually work?

**2026-08-19.** Harness: [`hard-easy-birthday.py`](hard-easy-birthday.py), run
as root on Linux 6.8 with nftables.

## The question

Row 8 of the Phase 4 topology table — a node behind a **symmetric** NAT talking
to one behind a **port-restricted cone** — stays on the relay. It is the most
likely real pairing there is: a CGNAT subscriber talking to somebody on an
ordinary home router.

The published technique for it is the birthday method: the hard side opens *N*
sockets toward the easy side's one knowable address, the easy side sends *M*
probes to random ports at the hard side's external address, and a collision
opens a path. Third-party analysis puts it at **64% in under two seconds** for
this pairing, against **0.01% after twenty seconds** when both sides are hard.

Before spending the architectural cost that technique implies — see below — the
question was whether it works against *our* NAT flavours, which are the ones
`crates/karst-disco/tests/nat_matrix.rs` pins and `bins/karstd/tests/tailnet.rs`
runs the product across.

## Result

It works, and the arithmetic predicts it closely enough to design against.

| N sockets (hard) | M probes (easy) | Packets | Measured | Trials | Predicted |
|---|---|---|---|---|---|
| 128 | 128 | 256 | **20%** | 40 | 22% |
| 256 | 256 | 512 | **60%** | 20 | 64% |
| 512 | 512 | 1024 | **95%** | 20 | 98% |

Prediction is `1 − (1 − N/K)^M` with `K = 64511` usable ports. Measurement runs
slightly under it at every point, consistently, which is what one expects when a
few of the *N* mappings collide by chance and the effective target set is
marginally smaller than *N*.

The blast itself takes **~1 ms**. Wall-clock cost is dominated by everything
except the probing.

### The design consequence, which is not the obvious one

**Bigger is cheaper.** Success per round is low enough that retrying is the
tempting design, and it is the wrong one:

| Strategy | Packets for ≥95% |
|---|---|
| 256×256, retried until it lands | ~1536 (three rounds at 60%) |
| 512×512, one round | **1024** |

One large round beats several small ones, because each retry re-pays for a fresh
set of mappings while the birthday curve is superlinear in *N·M*. A design that
"starts small and escalates" spends more traffic to reach the same place.

## What this does not settle

**The rate budget.** `aven-v1.md` §7.5 says a node MUST NOT emit more probe
traffic to a peer than that peer has authenticated itself to it. The existing
budget is already 16 candidates × 4 probes = 64 datagrams per advertisement;
512 probes is eight times that, on the strength of one `CallMeMaybe`.

The mitigating structure is that a blast goes to **one** address rather than
sixteen. The unresolved question is whether that address can be corroborated.
A node learns its *own* reflexive address from a reflector (§7.6) but learns its
*peer's* from the peer, which §1.1 explicitly allows to be malicious — so as
specified there is nothing stopping a peer from naming a third party and having
1024 datagrams sent at it. Closing that needs the relay to vouch for the source
address of the peer's own Ponor connection, which is a protocol change and is
not in this measurement.

**The architectural cost is confirmed, not avoided.** The hard side needs *N*
sockets held open simultaneously, because a socket is what earns a distinct
external mapping toward the one address the easy side is reachable at. Sending
to many destination *ports* from a single socket does not substitute: a
port-restricted symmetric NAT admits a packet only from the exact source its
mapping was created toward. The winner is one of the *N* sockets, so **the
datapath has to move to it** — which is in direct tension with `aven-v1.md` §4's
single shared socket, and is a change to `karstd`'s datapath rather than to
`karst-disco`.

## Two fixture defects found on the way, both worth reading

Neither is about the technique. Both are about measuring it, and both produced a
confident wrong answer first.

**The first run reported 0/6 where 64% was predicted.** The cause was finding 23
recurring one hop over. A's probes are addressed to `B_OUT:P`, which is the
*NAT's own outer address* — so with no input filter they are delivered to the
NAT namespace itself, which has no listener, so the kernel answers ICMP
unreachable and **confirms a conntrack entry** for `(A_OUT:R → B_OUT:P)`. That
entry occupies the reply tuple the inside host needs, so when B later wants a
mapping toward `A_OUT:R` it cannot keep port `P` and masquerade allocates a
fresh one. A packet capture showed it plainly:

```
10.95.0.3.64251 > 10.95.0.2.2291      ← B's "cone" NAT, on a port it never advertised
```

A cone behaving as a symmetric NAT, for the second time in this project, for
the same reason. The fix is the same: a DROP on the **input** hook at filter
priority 0, which runs before conntrack's confirm hook so the entry is never
confirmed. `bins/karstd/tests/tailnet.rs` already carries it; this fixture did
not.

**The diagnostic that was supposed to find that read an unreadable file.** The
first attempt to see A's mappings used `/proc/net/nf_conntrack`, which is not
readable inside these namespaces — so it reported "A's packets never left" when
the packets were leaving perfectly well. `tcpdump` on the bridge answered in one
run what the `/proc` reader had confidently got wrong.

The transferable rule: **when an experiment disagrees with a well-established
prediction, suspect the instrument before the theory** — and confirm the
instrument can observe a *known-good* case before trusting it on an unknown one.
The oracle run added here does exactly that: it tells the easy side one of the
hard side's real ports and checks the hit lands, which fails loudly if the
fixture is incapable rather than the technique unlucky.

## Reproducing

```sh
sudo python3 docs/measurements/hard-easy-birthday.py [trials] [N] [M]
```

It builds and tears down its own namespaces (`bd-*`) and leaves nothing behind.
It cannot run at the same time as any other privileged suite in this repository.

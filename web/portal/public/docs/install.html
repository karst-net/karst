Install and verify Karst

Download the installer for your platform from the Download page. Before installing, compute its SHA-256 checksum and compare it character-for-character with the checksum shown beside that release. Do not install an artifact whose checksum differs — download it again from the portal, and if it still differs, contact your administrator.

macOS

  1. Download karst-client-macos.pkg and verify it: 
    sha256sum karst-client-macos.pkg
    It is signed and notarized, so Gatekeeper accepts it on a clean machine without an override.
  2. Install it, either by double-clicking the downloaded file or from a terminal: 
    sudo installer -pkg karst-client-macos.pkg -target /
  3. The package installs karstd and karst to /usr/local/bin, an example configuration at /etc/karst/karstd.toml.example, and the Karst Status menu bar app in /Applications. It also installs the karstd LaunchDaemon, but does not start it — there is no /etc/karst/karstd.toml yet, and starting a daemon with nothing to run on would only hand you a crash loop.
  4. Continue with configuring the client from the admin console below.

To remove Karst from a Mac: sudo /usr/local/bin/karst-uninstall.

Linux

  1. Download the karst-client-linux package matching your distribution and CPU architecture and verify it: 
    sha256sum karst-client-linux_<version>_amd64.deb   # or the .rpm / arm64 build you downloaded
  2. Install it: 
    # Debian, Ubuntu (amd64 or arm64)
sudo apt install ./karst-client-linux_<version>_amd64.deb

# Fedora, RHEL (x86_64 or aarch64)
sudo dnf install ./karst-client-linux-<version>.x86_64.rpm
    apt and dnf resolve dependencies from a local file; dpkg -i or rpm -i work too but leave you to install any missing dependency by hand.
  3. The package installs karstd and karst to /usr/bin and a karstd systemd unit, but — same as macOS — does not enable or start it: karstd exits non-zero with no /etc/karst/karstd.toml, and a service that restarts forever is a worse first impression than one that waits.
  4. Continue with configuring the client from the admin console below.

To remove Karst from a Linux host: sudo apt remove karst-client-linux or sudo dnf remove karst-client-linux.

Configuring the client from the admin console

Installing the package gets the binaries and the service definition onto the machine. The client does nothing until it is configured with where to enroll and what key to enroll with — and that key comes from your organization's admin console.

  1. Generate the node's key — the same command on macOS and Linux. It never leaves this machine: 
    sudo sh -c 'umask 077 && karstd genkey > /etc/karst/node.key'
sudo chmod 600 /etc/karst/node.key
  2. In the admin console, open Setup (on a new deployment) or Auth keys → Create auth key, and note down three things:
    • the coordination server's public URL, entered or shown in that view;
    • the one-time enrollment key it issues — it is shown only once, so copy it immediately; and
    • the server's KEM and signature pins. These are not printed by the console — your administrator reads them from the coordination server's own startup log the first time it runs, and they do not change afterward.
  3. Write /etc/karst/karstd.toml with all four of those values. This is the same file on both platforms: 
    [node]
listen = "0.0.0.0:51820"
interface = "karst0"
private_key_file = "/etc/karst/node.key"

[control]
server = "http://karst.example.com:33073"
server_kem_pin = "<from the server's startup log>"
server_verify_pin = "<from the server's startup log>"
setup_key = "<the one-time key from the console>"
cache_file = "/var/lib/karst/netmap.cache"
    server is http://, not https://, even though the console itself is served over TLS — the control channel is its own protocol, authenticated by the two pins below rather than by TLS, and writing https:// here does not add encryption the daemon knows how to speak. Ask your administrator for the address if this one does not resolve for you; it is not necessarily the same host or port as the console. identity_key_file can be left unset — karstd creates /etc/karst/identity.key itself on first run. Both pins are mandatory: a node that trusted only one of them would connect but silently lose forward secrecy, which is worse than refusing to start.
  4. Validate the configuration before starting anything: 
    sudo karstd check --config /etc/karst/karstd.toml
  5. Start the service. 
    # macOS
sudo launchctl bootstrap system /Library/LaunchDaemons/dev.karst.karstd.plist

# Linux
sudo systemctl enable --now karstd
  6. Confirm it enrolled, both locally and in the console. Locally: 
    karst status
    reports the peer's session state and whether its path is direct or relay — a brand new node is relayed first and typically goes direct within seconds. In the console, open Machines and confirm the new device has a current observation and crypto posture.

If the node never appears, or the console's Machines view goes stale, re-check the server URL and pins before creating another enrollment key — a wrong pin fails silently rather than with an error naming it. Never paste an enrollment key or a pin into a ticket, chat, or shell history you do not control.

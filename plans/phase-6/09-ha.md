# HA

**PLAN.md Phase 6, workstream 9 · W5–W8 · SRE.**

This is the detailed plan behind [00-overview.md](00-overview.md) §2 item 9.
It is a re-baseline against the tree on 2026-09-04. Every hostname below
(`shannon`, `turing`, `lovelace`) is a real host already used by
[04-pentest.md](04-pentest.md); every IP address is a placeholder
(`203.0.113.0/24`, RFC 5737) — this is a public repository.

The overview's own risk table already sets the bar this plan must not soften:
*"HA's RTO/RPO becomes a document instead of a drill... The exit line for #9
is 'tested', not 'documented'; schedule an actual failover in W8, not a
writeup of one."* Nothing in this plan is done until a real failover has been
run against real hosts with a real number written down.

## 1. Outcome and scope

An operator can run `karst-control` as more than one process against a
replicated Postgres cluster, survive the loss of either the primary database
or any one `karst-control` process without an admin losing use of the
console or a node losing its session for longer than a measured, published
number, and recover from total data loss using a backup that has actually
been restored once.

In scope:

- Postgres as a two-node (primary + streaming replica) cluster, not the
  single instance §2 of the overview already credits as done;
- removing the two pieces of in-process state that make today's
  `karst-control` unsafe to run as more than one replica (§3.2, §3.3);
- a documented, scripted, and drilled promotion procedure for the Postgres
  replica, with a measured downtime number;
- a documented, scripted, and drilled backup/restore procedure, with a
  measured data-loss window;
- a `deploy/compose/ha/` overlay demonstrating the multi-host topology this
  requires, since the single-host `deploy/compose/docker-compose.yml`
  (co-located control + relay on one box, per its own header comment) cannot
  express HA at all — a second container on the same host is not a second
  failure domain.

Out of scope, recorded now per the overview's own §6 discipline:

- **Automatic failover.** A consensus-managed auto-promotion stack (Patroni +
  etcd/Consul, or equivalent) is real infrastructure with its own failure
  modes, and one SRE has four weeks to deliver a *tested* number, not stand
  up and separately harden a second distributed system. v1 ships a scripted,
  operator-triggered promotion that a monitoring alert points at, and it gets
  drilled for real. Automatic failover is a candidate for Phase 7, once this
  workstream's manual procedure has run in anger at least once.
- **Horizontal scaling of the relay or TURN server.** Both are already
  effectively stateless per-connection proxies (`deploy/compose/`'s `relay`
  and `coturn` services); nothing here changes them, and neither is in the
  overview's item 9 scope.
- **Multi-region or geo-distributed deployment.** Two hosts, one control
  plane, one Postgres cluster. Cross-region replication lag, split-brain
  across regions, and follow-the-sun failover are not this workstream.
- **Zero-downtime schema migrations.** `gorm`'s `AutoMigrate` runs on
  `karst-control` startup today (`store/migration.go`); making that safe
  under a rolling multi-replica upgrade is real work this plan does not
  claim. Document the current constraint (upgrade with all replicas stopped,
  or accept a migration race) rather than silently assuming it away.

| Backup/restore | Nothing. `grep -rn "pg_dump\|pg_basebackup\|backup" deploy/ docs/` finds no scripts, runbook, or even a stub | A tested backup procedure, a tested restore procedure, and a runbook documenting both |
| Bootstrap/state model | `deploy/compose/bootstrap.sh` generates `roster.toml`/`relays.json`/`policy.json`/`bootstrap.key` for a single host (per `docker-compose.yml`'s own header comment: *"the co-located deployment PLAN.md §5 makes the default"*) | These files are `karst-control`'s output, re-derived from Postgres-backed state on every write (`roster.toml` is rewritten every 25s already) — a second replica does not need its own copy, but the plan must say explicitly which host owns writing them in a two-host topology |

The two "in-process only" rows are the actual blocker. Postgres HA without
fixing them ships a system where the database survives but the application
layer silently breaks security and correctness guarantees the moment a
second `karst-control` process exists. This is the "hard 90%" the overview
already flagged, and it is a correctness project before it is an
infrastructure project.

## 3. Decisions to lock before implementation

### 3.1 Two hosts, not two containers on one host

`deploy/compose/docker-compose.yml`'s existing topology puts `control` and
`relay` on one box by design. HA needs a second failure domain: this
workstream's compose overlay assumes at least two hosts, each running its
own `karst-control` replica, with Postgres primary and replica placed on
either the same two hosts or a third pair — the plan does not mandate
co-locating Postgres with `karst-control`, only that primary and replica
Postgres are never on the same host as each other. The exit demonstration
(§7) uses `shannon` (existing primary, per [04-pentest.md](04-pentest.md))
and `turing` (already enrolled as a Karst node in that same pentest) as the
two hosts, since both are real and already reachable.

### 3.2 Session eviction becomes Postgres-backed, not distributed-locked

Do not replace `sync.Map` with a distributed lock service. Add a
`control_sessions` table (§4) to the store already required for HA and use
it as the cross-replica source of truth:

- On authentication, a replica `UPSERT`s a row keyed by the identity's
  ML-DSA public key, storing its own replica ID, a session token
  (comparable the same way today's `*sessionHandle` pointer is — a fresh
  random value per connection, not reused), and a heartbeat timestamp.
- Postgres `LISTEN`/`NOTIFY` (already available, no new dependency — this is
  the reason to solve both this and §3.3 with the same mechanism) broadcasts
  the identity's public key and the new owning replica ID to every replica
  on connect. A replica that held that identity's *local* `sync.Map` entry
  and does not match the new owning replica ID cancels its local session
  exactly as `service.go:208`'s existing `previous.(*sessionHandle).cancel()`
  already does today — the eviction mechanism itself does not change, only
  how a replica learns it lost.
- The local `sync.Map` remains as the fast path for same-replica lookups
  (most read traffic never needs Postgres); the table and `NOTIFY` are the
  cross-replica synchronization layer, not a replacement for it.
- A replica that misses a `NOTIFY` (reconnect gap, restart) reconciles by
  reading `control_sessions` for any identity whose stored replica ID no
  longer matches its own live sessions on startup — this is what makes the
  design safe against a dropped notification rather than relying on it.

This keeps `TestSecondSessionForSameIdentityEvictsFirst`
(`server/management/internals/karst/control/service_test.go`, added for
#87) passing unmodified for the same-replica case and adds the
cross-replica case as new coverage (§6).

### 3.3 Push fan-out becomes Postgres-backed the same way

`PeersUpdateManager.SendUpdate` gets a second path: after the existing
local-map lookup (found or not), it also issues a `NOTIFY` on a
per-deployment channel carrying only the peer ID — never the payload, matching
the existing design where `notificationChannels` are already
"edge-triggered invalidations", not payload carriers (`updatechannel.go`'s
own comment). Every replica's `PeersUpdateManager` subscribes to that
channel; on receipt, a replica checks its *own* `peerChannels`/
`notificationChannels` maps for that peer ID and delivers locally exactly as
`SendUpdate` already does — a replica that doesn't hold that peer's stream
simply finds nothing and no-ops, which is the correct behavior. This closes
the silent-drop gap in §2 without changing the wire contract a connected
peer sees.

[GitHub issue #75](https://github.com/karst-net/karst/issues/75) (push
fan-out computing a `SyncResponse` a Karst node discards, carried forward
from Phase 5 per the overview §0 item 1) is not fixed by this workstream —
but broadcasting a `NOTIFY` to every replica for every peer update does raise
the fan-out rate the issue is about, so re-estimating #75 belongs in this
workstream's write-up even though fixing it does not.

### 3.4 Replication mode: asynchronous by default, documented trade-off

Postgres streaming replication defaults to asynchronous. Synchronous
replication (`synchronous_commit = on` with `synchronous_standby_names` set)
gives a zero-data-loss RPO but makes every write wait on the replica's ack,
including over a real cross-host network — turing/shannon are on the same
LAN today, but nothing about this design should assume that stays true. Ship
async as the default, document the RPO it implies (§7's drill measures it
rather than asserting it), and document synchronous replication as an
operator-selectable trade-off for a deployment that wants zero data loss
over lower write latency. Do not silently pick one and call the other
unsupported.

### 3.5 Promotion is a script, not a person's memory

`scripts/pg-promote.sh` performs the promotion (`pg_ctl promote` or the
equivalent for the packaged Postgres version) and the accompanying
`karst-control` restart/reconfiguration needed to point every replica at the
new primary's DSN. A human still decides *when* to run it — v1 has no
automatic failover (§1) — but the mechanics are not a runbook of manual
`psql` commands typed under pressure. The drill in §7 runs this script, not
a paraphrase of it.

### 3.6 What a `karst-control` replica needs to stop assuming

Beyond §3.2/§3.3, grep `server/management/internals/karst` and
`server/management/server` for any other package-level mutable state
initialized once at process start (in addition to the two already found) —
this decision exists so the implementer does not stop at the two findings
this plan's research pass already made and assume the search is complete.
Anything found gets the same treatment: Postgres-backed cross-replica state
with a local fast-path cache, not a distributed lock.

## 4. Data model and configuration additions

New table, migrated the same way every other `SqlStore` table is
(`server/management/server/store/migration.go`'s existing `AutoMigrate`
path — §1's "out of scope" note on zero-downtime migration applies here same
as any other schema change):

```go
type ControlSession struct {
    IdentityPubKey string    `gorm:"primaryKey"`
    ReplicaID      string
    SessionToken   string
    LastSeenAt     time.Time
}
```

`ReplicaID` is a stable value per `karst-control` process — a config-provided
value (`KARST_REPLICA_ID`, defaulting to hostname if unset) rather than a
randomly generated one, so operational logs and the diagnostics bundle
(workstream 8) can name a replica consistently across restarts.

New environment/config surface, following the existing `NB_STORE_ENGINE_*`
naming:

- `KARST_REPLICA_ID` — this replica's stable identifier.
- `KARST_HA_NOTIFY_CHANNEL` — the Postgres `NOTIFY` channel name for session
  and peer-update broadcast, defaulting to a fixed value so a fresh
  deployment needs no extra configuration to get the cross-replica behavior;
  overridable only because a shared Postgres instance hosting more than one
  Karst deployment (unusual, but not disallowed elsewhere in the store
  config) must not collide channels.
- Postgres primary/replica DSNs reuse the existing
  `NB_STORE_ENGINE_POSTGRES_DSN` — HA does not invent a second config
  surface for "the other Postgres," since a promoted replica simply becomes
  the DSN every replica already points at (§3.5).

## 5. Implementation sequence

### W5 — remove the two single-replica assumptions (§3.2, §3.3)

1. Add the `control_sessions` table and migration.
2. Wire `LISTEN`/`NOTIFY` into `Service` (session eviction) and
   `PeersUpdateManager` (push fan-out), keeping both local maps as the
   fast path per §3.2/§3.3.
3. Add the reconciliation-on-startup path for a replica that missed
   notifications while it was down.
4. Complete §3.6's search; fix anything else found the same way.
5. New tests: two in-process `Service`/`PeersUpdateManager` instances
   sharing one real Postgres connection (not mocked — `NOTIFY` timing is
   exactly the thing worth testing for real), proving cross-instance
   eviction and cross-instance push delivery. This is the gate before any
   infrastructure work starts — running two `karst-control` replicas
   against unreplicated single-instance Postgres for this step is
   sufficient and deliberately does not require the replication cluster
   yet.

### W6 — Postgres replication and the compose overlay

1. Stand up primary + streaming replica Postgres, async per §3.4, with
   `pg_hba.conf`/`postgresql.conf` changes checked into
   `deploy/compose/ha/` rather than hand-edited on the host.
2. Write `scripts/pg-promote.sh` (§3.5).
3. Build `deploy/compose/ha/` as a per-host overlay: each host runs its own
   compose file pointing at the shared Postgres DSN and its own
   `KARST_REPLICA_ID`; document which host's `bootstrap.sh` output
   (`roster.toml`, `relays.json`, `policy.json`) is authoritative and how a
   second `karst-control` replica gets the same state without re-running
   bootstrap (it reads the same Postgres-backed account/policy data — the
   files remain the relay's own admission input per the existing 25-second
   rewrite, produced by whichever replica currently owns that duty, not by
   every replica independently).
4. Confirm a fresh two-replica deployment from published artifacts
   (`ghcr.io/karst-net/karst-control:dev` today; a real tag once one exists
   for this drill, following the `v0.0.0-*` throwaway-tag pattern
   [04-pentest.md](04-pentest.md) established) enrolls a node correctly
   through either replica.

### W7 — backup/restore

1. `scripts/pg-backup.sh`: `pg_basebackup` (base backup) plus WAL archiving
   configuration, not a bare `pg_dump` — a base backup + WAL replay is what
   makes a real point-in-time RPO number possible; a logical dump alone
   cannot express "data loss window," only "data as of the last dump."
2. `scripts/pg-restore.sh`: restore from a base backup and replay WAL to a
   target point in time.
3. Backup/restore runbook: what runs on a schedule, where backups are
   stored (explicitly not "on the same host as the primary" — a backup
   restore drill that restores from the disk that just failed proves
   nothing), and the exact commands an operator runs during an incident.
4. Drill the restore once here, informally, before §7's formal timed drill —
   finding "the restore script has a bug" during the timed drill wastes the
   measurement, not just the time.

### W8 — the drills that produce the numbers this workstream exists for

1. Run §7's failover drill for real, against `shannon`/`turing`, and record
   the number.
2. Run §7's backup/restore drill for real, and record the number.
3. Write the HA section of the operations manual (feeds workstream 11
   directly, per the dependency graph's `HA → Docs` edge) from what was
   actually run, not from this plan's description of what should be run.

## 6. Security and correctness tests

- `TestSecondSessionForSameIdentityEvictsFirst` continues to pass unmodified
  (§3.2) — same-replica eviction is not a regression target.
- New: a cloned identity connecting to replica B while the legitimate
  session is held on replica A is evicted within one heartbeat/`NOTIFY`
  interval, proven against two real `Service` instances sharing one
  Postgres connection.
- New: a replica that was offline when an eviction `NOTIFY` fired correctly
  evicts its stale local session on the reconciliation pass after it
  reconnects, proving the design doesn't depend on `NOTIFY` never being
  missed.
- New: a route/peer/policy change handled by replica A produces a delivered
  push to a peer whose stream is held on replica B, proven the same way.
- A `karst-control` replica that loses its Postgres connection entirely
  fails closed on new session authentication (refuses new connections
  rather than accepting them un-tracked) but does not tear down sessions it
  already holds locally — losing the database should degrade availability
  for new connections, not silently disable the eviction guarantee for
  existing ones.
- Promotion drill (§7) is itself a correctness test: every node connected
  to any replica at the moment of promotion reconnects and resumes without
  a manual step on the node side.
- `go test ./management/internals/karst/control/... -race` and
  `./management/internals/controllers/network_map/update_channel/... -race`
  both pass with the new cross-replica paths — `-race` matters more here
  than in most of this codebase, since the whole point of this workstream is
  concurrent access to shared state across processes.

## 7. Exit demonstration

From a two-replica deployment installed from published artifacts, `shannon`
running the primary Postgres and one `karst-control` replica, `turing`
running the streaming replica and a second `karst-control` replica, both
behind a shared entry point (round-robin is sufficient — §3.2/§3.3 make this
correct without sticky routing):

1. Enroll `lovelace` as a node. Confirm it can land on either replica
   (restart the client a few times against each, or simply show both
   replicas' logs seeing the connection over repeated enrollments) and
   receives netmap pushes correctly regardless of which replica handled the
   triggering change.
2. Clone `lovelace`'s identity key material (the same attack
   [04-pentest.md](04-pentest.md) §9.7 used to find #87) and connect the
   clone to the *other* replica from the one the legitimate session is on.
   Show eviction still fires — this is the regression test for #87 that
   matters most, since it's the one an HA rollout could silently reintroduce.
3. Kill `shannon`'s Postgres primary. Run `scripts/pg-promote.sh` against
   `turing`'s replica. Measure and record: (a) how long `karst-control` on
   both hosts takes to resume serving reads/writes against the new primary,
   and (b) whether `lovelace`'s active session survived or reconnected, and
   how long that took. This pair of numbers is the RTO the exit criteria
   require.
4. Restore `shannon`'s Postgres as a fresh streaming replica of the new
   primary (`turing`), proving the topology is recoverable, not a one-shot
   drill that leaves the deployment in a degraded state afterward.
5. Take a backup with `scripts/pg-backup.sh`, then deliberately corrupt or
   drop data, then restore with `scripts/pg-restore.sh` to a point before
   the corruption. Measure and record the actual data-loss window (RPO) —
   the gap between the last archived WAL and the corruption, not an assumed
   number.
6. Kill one `karst-control` replica process (not the database) while
   `lovelace` is actively connected to it. Confirm the client reconnects
   through the other replica without operator intervention and measure how
   long that takes.

Evidence retained with the phase gate: terminal transcripts of the promotion
and restore scripts running, `journalctl`/application logs from all three
hosts spanning each drill, the measured RTO/RPO numbers themselves, and the
operations-manual HA section written from this run.

## 8. Definition of done

- Two `karst-control` replicas on two hosts serve a shared Postgres-backed
  account without either the duplicate-identity eviction guarantee (#87) or
  netmap push delivery silently breaking for a peer on the "wrong" replica —
  proven by §6's tests, not asserted from the design alone.
- A Postgres primary can be lost and a documented, scripted promotion
  (`scripts/pg-promote.sh`) brings a streaming replica up as the new primary
  with both `karst-control` replicas resuming service — and an actual RTO
  number from §7's drill is recorded in the operations manual, not this plan.
- A documented, scripted backup (`scripts/pg-backup.sh`) and restore
  (`scripts/pg-restore.sh`) procedure has been exercised for real, and an
  actual RPO number from §7's drill is recorded in the operations manual.
- The promoted-replica and restored-backup topologies are themselves left in
  a recoverable state at the end of each drill, not a one-way trip.
- `deploy/compose/ha/` gives an operator a working two-host starting point
  rather than requiring them to invent the multi-host topology from the
  single-host `docker-compose.yml` by hand.
- No new distributed coordination service (etcd, Consul, Patroni) was
  introduced — the design deliberately reuses Postgres, which HA already
  requires, per §1's "what this workstream does not do."
- [GitHub issue #75](https://github.com/karst-net/karst/issues/75) has a
  written re-estimate reflecting the higher fan-out rate the cross-replica
  `NOTIFY` broadcast introduces, even though this workstream does not fix it.
- Any discovered high/critical finding in the cross-replica session or push
  logic — a way to defeat eviction, or a way to silently drop a push, under
  realistic multi-replica operation — is fixed and re-tested before the
  public beta gate, per the overview's §7 exit criteria.
